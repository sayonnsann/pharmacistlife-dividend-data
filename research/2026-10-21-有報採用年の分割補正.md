## 補正の仕様と批判的再確認

1. 読込時の`valid_yuho_adoption`による採用判定・来歴検査は変更していない。採用値convertedはdisplaySeriesの値に一致し、同年のstreakSeriesと3%以内で一致する必要がある。buildでも未補正のstreakSeriesに対して再検査する。参照値0は採用値も0の場合のみ許可、3%の境界と`1e-12`の丸め許容は既存判定と同じ。
2. 採用年のappliedEventsの各イベントがrecordのappliedActionsに含まれるかを効力日と新株/旧株の比率で照合する。実入力のappliedActionsは`ratio`、appliedEventsは`oldShares/newShares`を持つ。eventIdの形式差や1→2と2→4の表記差は許容し、日付違い・比率違い・欠落は検査エラー。採用年のappliedEventsが空で、record側にイベントがある逆向きの差は停止条件にしない。
3. `adjustment_for_unadjusted_series(adjustment, streakSeries, applied_actions=record.appliedActions, ...)`で既存系列に未反映のイベントを選び、その結果をseries_adjustmentとして共用する。最新期末以前のイベントとappliedActionsにある効力日のイベントを除く既存処理は変更していない。
4. 有報採用年へ`displaySeries[year] * adjustment_factor_for_period(series_adjustment, year, fiscal_month=fiscal.get("fiscalMonth"), field="dividend")`を一度だけ適用する。補正済みstreakSeriesの値へさらに掛けない。採用年以外の丸め処理は既存どおり。
5. rawのbasis・componentsのbasisDate・asOfを補正の分岐や除外に使わない。asOfが未来の採用は従来どおり拒否する。台帳の未来イベントの除外、provisionalの配当補正、台帳間のeventId重複処理は共通の既存処理に従う。

| 再確認項目 | 判定 | 根拠 |
|---|---|---|
| 二重補正していないか | 一致 | 未補正displaySeriesに共通の残り係数を一度だけ掛ける。SPKの2020-04-01分割はappliedActionsにあるためseries_adjustmentへ入らず、2026-04-01分割だけ×0.5 |
| SPK 13.25・12.75 | 一致 | 合成入力テストに加え、実入力のSQLite出力でもassert |
| basis不明・調整済みの除外を撤回したか | 一致 | 除外関数を削除。両basisの採用年が補正後もannualに残るテスト |
| 消える年がないか | 一部未達 | 検査通過3,466社は0年。停止350社の新規出力は生成できず、HEADの7,631年が影響対象 |
| 公開検査を緩めていないか | 一致 | `public_dividend_policy.py`は変更なし。unsafe display検査、公開payload検査、外部値の流出防止テストを維持。整合性検査を追加 |
| 停止時の既存DB保全 | 一致 | エラー時に公開先を置き換えず、既存SQLiteのバイト列が同一であることをテスト |

## 前回の1,030年の表示除外との関係

前回の「basis不明1,019年・調整済み11年、計146社1,030年を表示除外」は今回の方針では撤回した。basisによる除外は0年。

- 検査通過99社に属する771年（不明767年・調整済み4年）は、今回のSQLiteにもすべて残る。
- 残る47社259年（不明252年・調整済み7年）は、上記350社の検査停止に含まれる。basisにより年度を落としているのではなく、appliedEventsとappliedActionsの不一致により会社のビルドが停止する。
- 99+47=146社、771+259=1,030年。従って「前回落とした1,030年が全社で今回出力された」とは報告できない。既存表示をすべて維持して新しい全社DBを作るには、入力側の基準整合性を解決する必要がある。edinet-direct入力の変更は今回の対象外。
